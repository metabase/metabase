# E2E to Unit

Choose the cheapest test layer that preserves the behavior's real source of confidence. Classify each `it()` independently. A mixed spec can contain both unit-test candidates and browser-essential tests.

## Investigate the behavior

For every candidate:

1. Read the test, its hooks, and the code of every helper it calls. Browser-only behavior, such as hover, ECharts interaction, or navigation, is often inside a helper.
2. List the user actions and assertions, including setup steps that incidentally protect product code. A `cy.intercept` that narrows the request beyond the endpoint (a query, a body, headers, or a method other than the endpoint's usual one) is an assertion on the request (for example `query: { exclude_uneditable_details: "true" }` in an enterprise run): if the app stops sending it, the stub does not match and the test fails. The Jest test must assert that request too. Treat each narrowing intercept matcher, each request body read through `cy.wait`, and each response check as part of the claim that it guards. Assert the request in the Jest test (its query, body, or that it was sent), and prove it with one mutant that drops or changes that request input and fails on that assertion. A response check (`its("response.statusCode")`, `response.body`) reads server output. In Jest the response is a mock, so asserting it proves nothing. It needs a backend test that asserts the same status or field for the same request (`split`), or an existing one (the delete proof), or the `it()` stays. An intercept that only spies on or delays a request, with no narrowing matcher and no read of the request, is setup. When the request is part of the claim, `await waitFor(() => expect(fetchMock.callHistory.called(url)).toBe(true))` is the request assertion, and a mutant that fails there counts. One `it()` can hold more than one claim (for example two issue numbers). Give each claim its own verdict. The row's result is `keep E2E` only when every claim is `keep E2E`. Otherwise it is the first of `split`, `convert`, `delete as already covered` that a claim has, and its `keep E2E` claims stay in the `it()` (see step 4 of "Convert one test"). Each claim gets its own proof: new mutants for a converted claim, and the step 3 proof of "Delete a test that is already covered" for a covered claim.
3. Apply the hard gates below to each claim. If a browser gate applies (any gate except the last two), the claim's verdict is `keep E2E`. If only a backend gate applies (one of the last two) and a backend test can own that part, do steps 4 to 6 for the claim, then give it `split`, or `delete as already covered` when existing tests cover every part of the claim. If only the server part is covered, the verdict is `split`, and step 2 of "Split a test" reuses that backend test. Otherwise the claim is `keep E2E`. If no gate applies, do steps 4 to 6 for that claim. When every claim has a verdict, go to the next candidate.
4. Trace each assertion to the production function, thunk, hook, reducer, component, or endpoint that causes it.
5. Search existing Jest and backend tests by issue number, product symbol, component import, and assertion text (also the literal values, such as `254`). Finish this search before you write a test. If an existing Jest or backend test makes the same claim, the verdict is `delete as already covered`. Another E2E test counts as coverage only if it stays, runs the same path against the real backend, and asserts the same thing. Quote its assertion in the report. Mutants cannot prove it in Jest, so the delete proof is that quote and, when a backend is available, a run of that test with "Run a Cypress spec". If that run fails, it is not coverage: the row is `convert`. If two Cypress tests in scope make the same claim, convert one, then delete the other as covered by the new Jest test. Mark the delete row "depends on" the convert row. Put both rows in the same group, on the same worker, with the convert row first. If the convert row ends as `keep E2E`, the dependent row is `keep E2E` for the same reason. If the convert row is skipped before it writes its Jest test, the dependent row becomes `convert`. A row that is skipped later keeps its Jest test and mutant proof (only its Cypress edits are undone), so its dependent row stays `deleted`.
6. Find the nearest existing Jest spec for the behavior owner. Choose the helper whose store runs the reducers and middleware that your claim depends on. Extend it before you propose a new Jest file. If the owner has no spec, create a colocated `<Owner>.unit.spec.ts(x)` with a `setup()` that takes a `SetupOpts` object.

## Apply hard gates

Keep the test in Cypress if its claim depends on any of these:

- ECharts, canvas, SVG geometry, chart coordinates, or tooltips
- real hover, focus, keyboard behavior, drag, resize, scroll, or layout measurement
- viewport or responsive behavior
- computed styles, such as a color or a size from CSS. jsdom does not apply CSS modules. If the style is not the claim, list it as confidence lost.
- browser history, navigation, URL round trips, clipboard, downloads, or printing. Navigation is a gate only when the claim is about the route, the URL, or the move between screens. A click that only reaches a screen or a route modal is setup, and Jest can test the screen or modal content.
- a workflow whose claim depends on state carried from one screen to another (for example an edit on screen A that must show on screen B). A move that only reaches the screen under test is setup.
- a claim whose expected result is a value that the backend defines and the frontend only reads, for example the fields of a driver's connection form, an engine key in the help panel, or a setting key shown to the user. A Jest test must write these values by hand, so it stays green when the backend renames one. This is a backend gate. Mock inputs and request fields that the frontend itself writes (for example `dashboard_load_id`, `has_field_values` in a fixture) are not this gate: list them as confidence lost.
- a real backend query, permission boundary, or persistence cycle, unless a backend test can own that part. Then the verdict is `split`.

Do not override a hard gate because a test is short, slow, flaky, or easy to mock. Do not extract one DOM assertion from a browser-dependent flow and call the whole E2E test replaceable.

When the frontend and backend each own part of the claim, recommend `split`: a Jest test for frontend decisions, a backend test for server behavior, and retained E2E coverage only for an otherwise unprotected seam.

## Judge Jest suitability

Recommend `convert` only when all are true:

- the assertion is deterministic without browser rendering or a real server;
- Jest can execute the same production code path;
- mocks stop at external boundaries and do not replace the subject;
- the replacement can name a production change that would make it fail;
- the claim of the E2E test is protected by the replacement.

The setup steps of the E2E test (for example the menu path that reaches the state) can lose coverage. If another test covers them, name that test. If no test covers them, list them as confidence lost in the report. This applies only to setup actions. A check in a shared navigation helper that only waits for the page's own load requests (`H.visitDashboard`, `H.visitQuestion`) is setup too: list it as confidence lost. A setup check that narrows a request (a query, a body, headers, or a method other than the endpoint's usual one), or reads a value that the claim depends on, is an assertion: it needs a Jest or backend test that reads the same thing at the same boundary, or the `it()` stays. If the lost part is the claim itself, the verdict is `split` when only server behavior is lost, and `keep E2E` otherwise.

**Nothing may be lost.** This rule is stronger than every "list it as confidence lost" in this skill. List each thing the E2E test checks for real, as its claim or on the side. Examples are a real save or request, a real server response, the URL or route, an analytics event sent to Snowplow and checked against its schema, a real token or license activation, and the OSS build when the test has the `@OSS` tag (Jest then needs a case with no enterprise plugin). After the change, each one must still be checked by one of these:
- the new Jest test, at the same boundary
- an existing Jest or backend test that you name
- an E2E test that stays, which you name

Search `e2e/` and the backend tests for each one. If you find no test for a check, the `it()` stays, with the verdict `keep E2E` (or `split` when only server behavior is lost and backend tests are allowed). Mock data that only sets up the claim is not lost. In the report, "confidence lost" lists each such check with the test that still covers it. It can never say "nothing covers it". A PR body has these sections: "What moved", "Proof that the new tests catch the bug" (one sentence on what a mutant is, then a table with one row per mutant: the Jest test, the file and the code broken on purpose, and the check that failed), "Does this PR lose any check?", and "Changes to the Cypress spec" (what was removed, that no `beforeEach`, helper or kept test changed so the other tests run as before, whether Cypress ran locally, and that CI runs the tests that stay). Name each test or file as a GitHub permalink at the branch's pushed commit, with the line on that branch (`https://github.com/metabase/metabase/blob/<sha>/<path>#L<n>`), not as a bare `:<line>`. Answer the question first ("No."), then list the data that the Jest tests mock (each endpoint and what it returns, and any mock setting or token feature), grouped by page or component. If the deleted Cypress test already faked the same responses with intercepts, say so: then the real server answer was not part of its claim. Then say what Jest therefore cannot check, then show that the deleted test was not the only test that checked it. For each real-server check, say what the kept test does and where the page reads the value (file name), for example "turns routing on through the real UI and server, then reads `router_user_attribute` from the real response". Do not write a bare list of "what still covers", because a reader takes it as a list of losses. An E2E test that you name as cover becomes protected. Add it to `target/e2e-to-unit/covers.md`. Before you move or delete an E2E test, read that file. A protected test stays, unless the claim it covers is also checked in some other place.

Use one of four verdicts: `convert`, `delete as already covered`, `split`, or `keep E2E`.

Rank convertible candidates by an existing Jest seam, narrow setup, direct assertions, low lost confidence, and the amount of Cypress runtime removed. Treat runtime as a tie-breaker, never as evidence of suitability.

## Report

For an audit of one spec, return a table with: exact `it()` title and path, behavior owner, browser dependency, backend dependency, existing cheaper coverage, verdict, proposed destination, and confidence lost. Recommend one first candidate and explain why rejected alternatives stay in Cypress. When you convert a single test, give each rejected candidate one line instead of the table.

For an audit of a folder, report file by file. Show the list in the reply, not only in a file:

1. **Files with tests to move.** One row per spec file: the spec path, then each test that can move, as `:<line> <short title> (<issue>)`. Group the tests of a file by verdict (convert, delete as already covered, split, trim). If the user asks for Jest-only work, list only the `convert` tests, and leave out every test that needs a backend or Clojure test.
2. **Files with nothing to move.** One row per spec file, with the reason in a few words (for example "real login flows", "only splits that need backend tests", "already covered by PR #NNNNN").
3. **Totals:** the number of files and tests for each verdict, and the tests you did not investigate.

Every spec file in the folder appears in exactly one of the two lists. Put the full rows (owner, covering test, target spec) in a file and give its path.

## Convert one test

Do these steps in order. Do not stop after the Jest test passes. If a claim's verdict becomes `keep E2E` during steps 1 to 3, undo that claim's edits with inverse edits, do not do step 4 for it, and report the reason. If no claim is left to move, do only the `git status` and `git diff` comparison of step 5, then report. When a row has more than one moved claim, do steps 0 to 3 (or the proof of "Delete a test that is already covered" or "Split a test") for every claim first. Do step 4 once for the row, after every claim has its final verdict.

0. Rows are named `row-<k>`: for a single test `<k>` is 1, and in a batch it is the row's number in the work list. If `target/e2e-to-unit/` already has `row-*` files from an earlier run, move them into a dated subfolder first, so that a new row creates its files fresh. Save the starting state: `git status --short` and `git diff HEAD` (it also shows staged changes). Also run `bun run type-check-pure` and save its output, and run the whole Jest spec that you will extend (no `-t`) and save its `Tests:` line (skip this for a spec that does not exist yet). Later type checks must show no error that is not in this output. Compare by file path and error code, because a worktree with linked `node_modules` can already have errors. The checkout can already have changes that are not yours.
1. Before the first edit to a Jest spec or test helper, copy it to `target/e2e-to-unit/row-<k>-jest-original-<file name>.txt` with `cp <file> <copy>`, one copy for each source file. For a spec that does not exist yet, record "new file" instead: its baseline is no tests, and an undo deletes it. Write the Jest test in the existing spec for the behavior owner. Test a pure function, reducer, or formatter directly. For a thunk or a component, reuse the spec's `setup()` helper and its real store or render helper. If that `setup()` waits for loading to end (for example `await waitForLoaderToBeRemoved()`) and your test holds a response back, add an option that skips the wait. Keep the old behavior as the default, so other callers do not change. Add new options in the form the `setup()` already has (an options object or positional arguments). Do not refactor it. For an existing positional `setup()`, this rule overrides the `SetupOpts` rule of `typescript-write`. Assert the same values the Cypress test asserted, read at the same boundary. If the Cypress test read a request body (`cy.wait` on an alias, then `request.body`), the Jest test must read the body of the request that the app sent, from `fetchMock.callHistory`. A callback argument such as an `onSubmit` prop is not the same boundary: the code between the callback and the request is not tested. Follow the `typescript-write` skill: add no type casts and no `// Unjustified type cast. FIXME` comments, even when nearby tests have them. Read parsed JSON as `unknown` and narrow it.
   - Give the Jest test the exact title of the Cypress `it()`. For a Cypress `forEach` over values, use `it.each` with `%s` where the title has the value. If one Cypress test becomes Jest tests in several specs, each one gets the same title. If it becomes two tests in one spec, both keep the title and add the part in parentheses, for example `"correctly displays models empty states (dismiss the banner)"`. Only a positive control that the Cypress test did not have gets its own title.
   - The Jest test must be as easy to read as the Cypress test. Keep its structure: the same steps in the same order. If the Cypress test calls named flow helpers (for example `executeCreateGlossaryTermFlow()`), write one Jest helper for each flow, with a close name, and make the test body a list of those calls. Lint requires a helper with assertions to start with `assert` or `expect` (for example `assertCreateGlossaryTermFlow`).
   - Call the thunk, hook, or function with the exact arguments that its production caller passes. Copy them from the caller. For a component, pass the props that the caller passes and that the claim depends on. Leave out props for display only.
   - If the caller builds an argument from app state (for example a hydrated UI parameter), you can build it by hand. List that in the confidence lost.
   - Use the values that the API really returns, for example `details: null`, not `undefined`. Read the backend schema or an existing API mock when you are not sure.
   - Give mock entities distinct ids (for example `dashcard.id` 10 and `card_id` 20). Equal ids hide a mutant that reads the wrong key. This also applies to other inputs: if the Cypress test uses equal values (for example interval 1 and offset 1), use distinct values and assert the output for them. Keep the Cypress values only when the claim is about those exact values.
   - To check a pending state, hold the response back with `defer()` from `metabase/utils/promise`. Use this order: wait until the request was sent (this `waitFor` only synchronizes the test, so it can come first), read the element, resolve the request, then assert the claim. Resolve every deferred mock before any claim assertion and before you await the completion of the pending operation. A mutant must fail on an assertion, not on a Jest timeout. A `findBy*` or `waitFor` on the claim that fails after its wait is an assertion failure. A mutant that fails in setup or at an earlier step, before the claim's assertion, does not count. Choose another mutant. In a form with required fields, choose one that keeps the form valid, so that Save still works. If the claim can only be read after a wait while the request is pending (for example a debounced document title), wrap that wait: `try { await waitFor(() => expect(...)) } finally { deferred.resolve(); }`. Then every path out of the test resolves the request.
   - Mock endpoints with helpers from `__support__/server-mocks`. If no helper fits, add one there. To hold a response back, let the helper accept a function that returns a promise (see the component example). Do not register raw `fetchMock` routes in a component test.
   - If the positive control shows that a value the Cypress test checked never appears (for example the UI shows `1234`, not `1,234`), check why the Cypress test passed. A Cypress assertion that passes in CI proves that the browser shows the value, so the claim is a browser gate (for example locale formatting), and its verdict is `keep E2E`. The only exception is a negative or loose assertion (`should("not.exist")`, a substring `contains`, a regex) that passes whatever the UI shows. If you are not sure that the assertion is of that kind, the verdict is `keep E2E`. Only for that exception did the Cypress check pass for the wrong reason. Then assert the value that does appear, and say so in the report.
   - A negative assertion ("no button", "no request") needs a positive control in the same setup that expects the opposite result. Without it, the test can pass for the wrong reason. Do not call the spec's `setup()` twice in one test: it registers named `fetchMock` routes, and the second call fails with `Adding route with same name as existing route`. Change the state in the same store (for example dispatch an action), or put the control in a second `it()` with the same setup.
   - If the frontend code path of the claim is behind an enterprise plugin (a `PLUGIN_*` hook or an `enterprise/frontend` component), the claim needs that plugin. A token that the Cypress test activates only for a backend part (sandboxing, permissions) needs no plugin in Jest: say so in the report. For a plugin path: Use the owner's enterprise Jest spec (under `enterprise/frontend/src`, or `<Owner>.enterprise.unit.spec.tsx`), or a `setup()` with an `isEnterprise` option. That setup sets `token-features` with `createMockTokenFeatures` and calls `setupEnterpriseOnlyPlugin("<plugin>")` or `setupEnterprisePlugins()` before render. Without the plugin, the code runs the OSS fallback, and a negative assertion can pass for the wrong reason.
   - For a component, follow `frontend/CLAUDE.md`. If the claim includes an interaction, act with `userEvent`. Find elements with `screen` role and text queries. Use a test ID only when the element has no accessible role, label, or text. Wait for UI state with `findBy*` or `waitFor`, not by flushing `fetchMock`.
2. Run only that test: `bun run test-unit-keep-cljs --runInBand --runTestsByPath <spec> -t "<pattern>"`. Jest reads `-t` as a regex over the full test name (the `describe` titles and the `it()` title). Use a pattern that matches only the new test, for example its issue number. Escape regex characters such as `(`, `)`, `.`, and `?`. Read the `Tests:` line, not the `Test Suites:` line. It must say `1 passed` (or `1 failed`), and every other test must be skipped. If the claim has a positive control in a second `it()`, give both tests the same issue number, and expect 2 tests to run. If more than one test runs, read the other test. If it makes the same claim and its mutant proof was not yet done, undo your test and use "Delete a test that is already covered". If the Delete recipe already sent this row back to `convert` (from its step 2 or step 3), keep your test and make the pattern more exact. Otherwise make the pattern more exact or rename the test. Use the same command and check for every mutant run. Also run `bunx oxfmt --write <spec>`, `bun run lint-oxlint -- <spec>`, and `bun run type-check-pure` now, so a fix does not come after the mutants. If the new test logs a warning, run one existing test of the same spec that renders the same component, with its own `-t` pattern. If it logs the same warning, the warning is not new. Fix a warning that only the new test causes.
3. Prove the test can fail. Before you mutate a production file, save its current `git diff <file>`. Make one small mutation that makes the claim false, run the test, and see it fail. Undo the mutation with the exact inverse edit. Then compare `git diff <file>` with the saved diff. Never use `git checkout <file>` or `git restore`, because they also erase other uncommitted changes in that file. Use at least two mutants: a wrong value (for a predicate, a wrong key, a wrong operand, or `&&` changed to `||`) and a removed check or statement. If you change the test after the mutants, run the mutants again. A change from oxfmt only (whitespace, line breaks, import order) does not need a new run.
   - Make each mutation and each undo with the Edit tool, one exact string. Do not use `sed` with shell variables. Some sandboxes refuse it, and a wrong pattern can edit other lines. Include one unchanged neighbor line in both the mutation and the undo strings. Then the undo still matches after a mutant deletes a line, and a mutant that copies a nearby value does not make the undo string ambiguous.
   - You do not need the original bug fix. Choose mutants that make the claim false. If `git log --grep <issue number>` finds the fix, its diff is a good source of mutants. A shallow history often does not have it.
   - If the behavior owner is ClojureScript (`.cljs` or `.cljc`), `test-unit-keep-cljs` uses the old compiled output. Run `bun run build-pure:cljs` after each mutation and again after each undo. If you skip the rebuild after the undo, every later Jest run tests the mutant.
   - If a mutant survives, find out why. If it does not make the claim false (an equivalent mutant), report it and add a different mutant. If it does make the claim false, the test is too weak. Fix the test.
4. Never delete or weaken an assertion of a `keep E2E` claim or of a kept seam, in any step. Before you edit any block of an E2E file (an `it()`, a hook, a local or shared helper), append the file path and the block's original text, with enough unchanged neighbor lines before and after it to be unique in the file, to `target/e2e-to-unit/row-<k>-cypress-original.txt`, where `<k>` is the row's number in the batch work list (the orchestrator gives each worker those numbers). For a single test, use `row-1`. The undo anchors on those neighbor lines. To undo one row in a spec that later rows also edited, first undo the later rows in reverse order, then undo the row, then put the later rows back from their `row-<j>-cypress-edited.txt` files (save that file for each row when the row is done). Create the file with the Write tool. To add a later block, Read the file and Write it whole again, or Edit its last line. Never Write only the new block, because Write replaces the file. Do not use a shell redirect. This also applies to a setup fix under "Run a Cypress spec". Each time this row deletes an import, a constant, or a helper in any E2E file, append the file path and the deleted lines to the same file. An undo of this row's Cypress edits puts all of this text back with the Edit tool, in reverse order of saving, then runs `bunx oxfmt --write` and `bun run lint-oxlint --` on each restored file. If lint reports an undefined name, another row of the same spec deleted it. Restore it from that row's saved file. Delete the Cypress `it()`. If another claim of the same `it()` stays in Cypress (`keep E2E`, or a kept seam of a split), remove only the actions and assertions that belong only to the moved claims, and keep the `it()`. A `should`, `expect`, or `cy.wait` that comes before a kept assertion in the same `it()` or hook stays, even when it belonged to a moved claim, because the kept assertion may depend on it. If its `describe` is now empty, delete the `describe` with its hooks and local helpers. Delete the spec file if nothing is left. Before that, copy it with `cp <spec> target/e2e-to-unit/row-<k>-<spec name>.deleted`. An undo recreates the file from that copy with the Write tool. Leave `e2e/support/timings.json` as it is, because CI updates it. Delete a block with the Edit tool. For a very long block, Edit its first and last lines as anchors. If the Edit tool cannot do it, print the first and last lines with `sed -n '<first>p;<last>p' <spec>`, then delete with `sed -i '' '<first>,<last>d' <spec>` on macOS or `sed -i '<first>,<last>d' <spec>` on Linux, with the numbers written literally. Check the lines around the cut afterwards. For each constant, import, or helper that the test used, search the whole repo (`e2e/` and the support files) for other callers. Delete it only when no caller is left. Then, if the Cypress spec still exists, run `bun run lint-oxlint -- <cypress spec>` and remove every unused import or variable that it reports.
5. Do the final checks after every mutant is undone:
   - Make the list of files to check: the Jest spec, the Cypress spec if it still exists, and every helper file you edited. Do not include a deleted file, because oxfmt and oxlint fail on a missing path. If the list is empty, skip the oxfmt and oxlint items, because oxlint with no path lints the whole repo.
   - `bunx oxfmt --write <files>`. Format first, so the next checks run on the final contents.
   - Run the Jest test again (the step 2 command), then the whole spec and every spec that imports a test helper whose existing behavior you changed. Compare with the step 0 result: no new failure.
   - `bun run lint-oxlint -- <files>`. Lint finds what the deletion left unused in those files.
   - `bun run type-check-pure`, and read any error in the files you changed.
   - Run the `typescript-review` skill on the diff of the files you changed. For a diff with only test files and test helpers, skip its accessibility, bundle-size, and analytics items. Fix each finding, except these, which you report and do not change: a finding on a Cypress assertion, action, or setup step that stays (a `keep E2E` claim or a kept seam), and a request to change an existing positional `setup()` to `SetupOpts`. If a fix changed a test, run its mutants again (step 3), then repeat step 5 from the oxfmt item.
   - If the Cypress spec still exists and you changed a hook, a shared helper, or a test that stays, run the spec as in "Run a Cypress spec" below. If you only deleted whole `it()` or `describe` blocks, lint is enough. Say in the report whether you ran the spec.
   - `git status --short` and `git diff HEAD`. Compare them with the step 0 state. The changes from step 0 are still there. Every new change is in a file you meant to change: the Jest spec, the Cypress spec, a helper file you edited or deleted, or, for a split, the backend test. No production file changed, and no mutant is left.
6. Report the Jest test, each mutant and its result, and the confidence lost. If you give commit commands, write them for the user. Do not run `git add`, `git commit`, or `git push`. For the confidence lost, search `e2e/` for the feature's UI text and the caller's name. Name the E2E test that still covers the lost part, or say that nothing does.

## Delete a test that is already covered

1. Do step 0 of "Convert one test". The whole-spec run is for the spec that holds the covering Jest test.
2. Name the existing test that covers the claim. When the claim has a frontend part and a server part (for example a request body and a response status), name one covering test for each part, and prove each with its own mutants in step 3. If a part has no covering test, the row is `split`. If the claim includes a request check, the covering test of the frontend part must read the same request at the same boundary (a `fetchMock` route matcher or `fetchMock.callHistory`). If it does not, the row is `convert`: continue with steps 1 to 6 of "Convert one test", and do not do steps 3 and 4 below. For a Jest test, run it with the step 2 command of "Convert one test" (a `-t` pattern that matches only that test). Use only the Jest command and the `Tests:` check of that step, not its oxfmt, lint, type-check, and warning items. If more than one test runs, make the pattern more exact. If two existing tests make the same claim, name either one. For a backend test, run it as in step 2 of "Split a test".
3. Prove that it protects the claim. If the covering test is another E2E test, the proof is the quote and the run from step 5 of "Investigate the behavior". Then go to step 4. Otherwise do step 3 of "Convert one test" against the existing test, except its "Fix the test" sentence: do not edit the existing test. For a backend test, follow the mutant and reload rules in step 2 of "Split a test". Every mutant that makes the claim false must fail the existing test. When the claim has a request check, one mutant must drop or change that request input and fail the frontend part's covering test on an assertion. Prove a backend covering test with backend mutants only. If a claim with a server part loses its frontend covering test, the row becomes `split` (a new Jest part, and the backend part proven as in step 2 of "Split a test"), not `convert`. A failure only in `afterEach` ("unmocked routes") does not count. If one survives and it is not an equivalent mutant, the claim is not fully covered. The row is `convert` from now on: leave the existing test as it is, and continue with steps 1 to 6 of "Convert one test" instead of step 4 below. For a backend test, the row is `split` from now on: leave the existing test as it is, and continue with steps 1 to 4 of "Split a test" instead of step 4 below. If you came here from step 2 of "Split a test", go back to that step and write a new backend test.
4. Do steps 4 to 6 of "Convert one test". The report names the existing test instead of a new one. If the covering test is a backend test, there is no Jest spec. In step 5, run the backend test again instead of the Jest test. The file list is then the Cypress spec (if it still exists) and the helper files you edited. If the covering test is another E2E test, skip the Jest run in step 5, and use the same file list.

## Split a test

1. Write the Jest part for the frontend decision. Do steps 0 to 3 of "Convert one test". A narrowing intercept matcher or a request body read is a frontend decision: write the Jest part for it. If the frontend only renders the value that the server computed, there is no frontend decision. Do step 0 only, say in the report that the split has no Jest part, and go to step 2.
2. Load the `clojure-write` skill before you edit any Clojure file, and follow it, including its readability check after each change. Do not follow its "Lint PR" step, which commits: lint with `./bin/mage kondo <file>` only, and never commit. If an existing backend test already makes the server claim, do not write a new one. Unless you came from step 3 of "Delete a test that is already covered" (that proof already failed), name it and prove it with steps 2 and 3 of that recipe (backend mutants). If that proof fails, leave the existing test as it is, and write a new backend test here. Do not go back to step 1. Otherwise write the backend part in the nearest existing backend test namespace for the server behavior. Run it with the `clojure-eval` skill: `(require '<source-ns> :reload)`, `(require '<test-ns> :reload)`, then `(clojure.test/run-test-var #'<test-ns>/<test>)`, and read the line "Ran 1 tests containing N assertions. X failures, Y errors." Use `clojure-eval` only if `clj-nrepl-eval --discover-ports` finds exactly one Clojure nREPL (not Babashka or shadow-cljs) in this checkout. Then use that port without asking. Otherwise (the command is not found, none, several, another checkout, a worktree, or no way to ask the user), use `./bin/test-agent :only '[<ns>/<test>]'`. The nREPL behind `clojure-eval` loads the main checkout's files, so it never sees a worktree's mutants. The same applies to `clojure-mcp` tools, although `clojure-write` says to always use them: in a worktree, use `./bin/test-agent`. Do step 3 of "Convert one test" with backend mutants: at least two, as for the Jest test. With `clojure-eval`, the REPL keeps the old code. After each mutation and after each undo, reload the source namespace with `(require '<source-ns> :reload)` before you run the test. `./bin/test-agent` starts a new JVM for each run, so it needs no reload.
   The backend test needs a positive control too: the same setup with a user or a setting that gives the opposite result. A claim about static driver data (a connection property in `metabase-plugin.yaml`) has no opposite setup: assert its shape in `GET /api/setting/engines` in the driver's test namespace, and say in the report that it has no positive control.
3. Before any edit to the Cypress spec, save the original text as in step 4 of "Convert one test". Keep the Cypress `it()` if a seam between the two parts has no other test, or if a claim of the `it()` has a browser gate. Keep those assertions. Then read `.claude/skills/e2e-test-create/SKILL.md` and `.claude/skills/_shared/cypress-conventions.md` with the Read tool (the first cannot be loaded with the Skill tool, and Read does not expand its `@` include of the second). If an unprotected seam exists, use only its Phases 0, 1, and 3 (research, code analysis, write the spec) to reduce the test to that seam plus the unchanged assertions of its browser-gated claims. The conventions apply to the seam part only. Copy the actions and the assertions of the browser-gated claims exactly, even where the conventions would merge, scope, pair them, or replace UI steps with API setup. Only the actions and setup of the seam part may be rewritten. Narrowing matchers and request reads in the seam part are seam assertions. Each original seam assertion stays, or is replaced by one that checks at least as much. Say so in the report. Then do the caller search and the `bun run lint-oxlint -- <cypress spec>` item of step 4 of "Convert one test". If the `it()` stays only for a browser-gated claim, do not rewrite it: do step 4 of "Convert one test" (remove only the moved claims' actions and assertions). Do not start, run, or kill a backend from that skill, and do not use its Phases 5 and 6, which change a test to make it pass. Run the test as in "Run a Cypress spec" below. If no such seam exists, do step 4 of "Convert one test".
4. Do steps 5 and 6 of "Convert one test". If the split has no Jest part, skip the Jest spec and the Jest run in step 5. Then the file list is the Cypress spec (if it still exists) and the helper files you edited. Do not give the backend test file to oxfmt or oxlint, because they check only JS and TS files. Run `./bin/mage cljfmt-files <file>` and `./bin/mage kondo <file>` on it, then run the backend test again. Include the backend test and its mutants in the report.

## Convert many tests

Use this when the request covers a spec or a list of tests, or a folder in batches of 10 rows. For a whole folder with one branch and one PR for each spec, use "Convert a whole folder".

1. Audit first. Do not edit files during the audit. A folder can have more than 100 `it()` blocks. Audit one spec file at a time, and stop the audit when the work list has as many rows as the batch (step 2). Start with the reproduction specs (`*reproductions*`), because they often hold one narrow claim per test. List the specs that you did not audit in the report. For each spec, do two passes:
   - Triage: find gate signals with a search, for example `grep -nE 'realHover|realPress|echartsContainer|cartesianChartCircle|moveDnDKitElement|cy\.location|cy\.url|cy\.go\(|cy\.viewport|have\.css|getBoundingClientRect|updatePermissionsGraph|blockUserGroupPermissions|downloadAndAssert|clipboard|signInAs(NormalUser|ImpersonatedUser|SandboxedUser)|signIn\("|activateToken' <spec>`. `signInAs…`, `signIn(` and `activateToken` are not gates. They point to a permission or an enterprise claim. A hit on a permission or backend gate (`updatePermissionsGraph`, `blockUserGroupPermissions`) points to `split`, not to a rejection in triage. More than one `visit` in one `it()` points to state carried between screens. A hit is only a hint: reject the test only when the hit is in its `it()` body or in a hook or helper that runs for it, and the gate is part of the claim. To map a hit to its test, read the spec file around the hit. Then read the body of each test that is left. Give the tests rejected in triage one line per spec file in the report: the spec, the number of tests, and the gates. A test that you investigate in full goes in the table, even when its verdict is `keep E2E`.
   - Shortlist: do "Investigate the behavior" in full for the tests that are left, one at a time, until the work list is full. Make the table from "Report" for them. List the other shortlisted tests as "not investigated" with a one-line guess.
2. Make a work list from the rows with `convert`, `delete as already covered`, or `split`. Group the rows by Cypress spec file. A row that depends on another row joins that row's group and comes after it. Order the groups by their cheapest row (see the ranking in "Judge Jest suitability"), and order the rows in a group the same way. If the checkout that will do step 7 is itself a worktree (`git rev-parse --git-dir` differs from `git rev-parse --git-common-dir`), so there is no main checkout to run Cypress from, a row that trims an `it()` that stays cannot finish. Mark it `skipped` at this step and do not write its Jest test. A skipped row deletes nothing, so its covered claims need no proof. Take the first 10 rows of this list into the batch. Leave the rest for the next batch.
3. Save the batch start state: `git status --short` and `git diff HEAD`. Also run `bun run type-check-pure` and save its output as the batch baseline, and run each Jest spec that the rows will touch as a whole file and save the result. In step 7, only a new failure is caused by a row: find that row, fix its test and run its mutants again, or undo that row and mark it `skipped`. If its Jest test must go, first undo the Cypress deletions of the rows that depend on it. In a batch, undo a Jest row by removing only its own added blocks with the Edit tool, not by restoring the whole file, because later rows may have added tests to the same spec. A row that reuses a helper that another row added depends on that row: same worker, after it, and undone before it. The final check compares the whole diff with this state.
4. Do each row with its full recipe ("Convert one test", "Delete a test that is already covered", or "Split a test"). Each row needs its own Jest test (for a delete row, the named existing test), its own mutants, and its own confidence lost. One passing run never proves two tests.
   - Before each row, save the state again. That row's step 5 comparison uses this state, so the changes of earlier rows are not new changes.
   - In each row's step 5 and in step 3 of "Split a test", skip the Cypress spec run, and in step 5 skip `typescript-review`. Step 7 below runs them once on the whole diff.
   - Keep the step 2 type check for each row that adds a Jest test, and skip the type check of step 5, because step 7 runs it. A row that only deletes Cypress code can skip both. Save the type-check baseline once, at step 3.
   - Before you add a server-mock helper, search for one that an earlier row added.
   - If every claim of a row turns out to be `keep E2E`, undo that row's edits with inverse edits, write the reason in the table, and go to the next row. Do not weaken the claim to make it fit.
5. Run rows one after the other in one checkout. A mutant in a production file breaks every other test that runs at the same time. To run in parallel:
   - Give each worker its own git worktree from the main checkout's commit (`git rev-parse HEAD`). The worker checks its own `git rev-parse HEAD` first. If they differ, it runs `git checkout --detach <sha>` before it applies any patch. If the batch start `git diff HEAD` is not empty, or the checkout has untracked files that the rows depend on, write that diff with `git diff HEAD --output=target/e2e-to-unit/batch-start.patch`, give the worker its absolute path and those files, and have it run `git apply <path>` before its first row. Right after that, the worker runs `git stash create` and saves the hash that it prints (an empty output means no change to save), and saves the list of untracked files (`git ls-files --others --exclude-standard`, one line per file) with a checksum of each (`shasum <file>`). This command does not change the worktree, the index, or the stash list. Give each worker one or more whole groups. Rows that share a Cypress spec, a Jest spec, a server-mock file, or a shared E2E helper go to the same worker. If two groups need the same shared file, give both groups to one worker. If this puts most rows on one worker, use fewer workers. Correct results are more important than speed.
   - Each worker prepares its worktree as in "Work in a new worktree" below.
   - Each worker does its rows one after the other, as in step 4, and writes its patch to a file: `git diff <saved hash> --output=target/e2e-to-unit/worker-<n>.patch` (or `git diff HEAD --output=...` when it saved no hash). It returns the patch path, its worktree path, and the list of the untracked files that are not on its saved list, plus each listed untracked file whose checksum changed. Do not paste a patch into a message, because that changes whitespace. Then the patch holds only the worker's own changes. It also returns its table rows, its mutant results, and the absolute paths of its `target/e2e-to-unit/` files. The orchestrator copies those files into its own `target/e2e-to-unit/` before step 7. It does not commit.
   - Workers do not run Cypress, because parallel Cypress runs fight over the backend port. For a split row with a kept seam, a worker writes the reduced test as in step 3 of "Split a test". A worker marks "needs Cypress run" on every row that leaves a changed `it()`, hook, or shared helper in a spec that still exists, including a reduced seam test. It names the spec and the changed test. The orchestrator runs these one after the other in step 7.
   - The orchestrator applies each patch file in the main checkout with `git apply <patch path>`, one at a time, copies the listed files from the worker's worktree, then checks that each reported Jest test is in the main checkout (search for its title). If one is missing, copy its file from the worker's worktree path, then check again. If a patch does not apply, give that group to a new worker again. Give it the current `git diff HEAD` of the main checkout as a patch file, plus the new files, to apply before its first row.
6. Stop taking rows when every row in the batch has a result. A row that ends as `keep E2E` does not get a replacement from the next batch. Go to step 7.
7. In the checkout that holds the combined diff, do step 5 of "Convert one test" once for the whole diff: format, every changed Jest spec as a whole file (not only `-t`), every Jest spec that imports a test helper whose existing behavior changed (search by the helper's directory, because many specs import their own `./setup`), lint, type check, `typescript-review`, and a run as in "Run a Cypress spec" for each Cypress spec that still exists and has a changed hook, shared helper, or kept test, and for each row marked "needs Cypress run". The list is every row marked "needs Cypress run" (in sequential mode, mark rows in the same way as a worker does in step 5), plus every spec where a fix in this step changed a hook, a helper, or a kept test. Compare with the batch start state from step 3. A new helper export, or a new option with the old default, changes no importer, so it needs no extra Jest run.
8. Report the final table with one more column: result (`converted`, `deleted`, `split`, `kept`, or `skipped` with a reason). Give each row its Jest test (or the existing test for a delete row), its mutants, and its confidence lost. Write commit commands in the report for the user. Do not run `git add`, `git commit`, or `git push`. In the commands you write, use `git add <files>`, never `git add -A` or `git add .`. Give one commit per row when the row's files are not shared with another row. Rows joined by any shared file (Cypress spec, Jest spec, helper, or server-mock file), also across groups, go in one commit. Say which rows the commit holds. Do not split a file between commits, because that needs interactive staging. If a file in a commit command already had changes at the batch start, say so next to the command: the commit also holds those changes. List the work-list rows that are still to do. Then ask the user before the next batch, even if the request said "all".

## Convert a whole folder

Use this when the user gives a folder and wants it done spec by spec. One Cypress spec gets one worktree, one branch and one PR, so that a reviewer reads one spec at a time. The work uses parallel agents in two phases, because most of the cost is in specs that have nothing to move, and in waiting for one spec before the next starts.

1. **Set up.** List the spec files of the folder with their `it()` counts. Leave out specs that an open PR already converts, and say so. Run the type check once in the main checkout and save it as `target/e2e-to-unit/typecheck-baseline.txt`. Every worker compares with this file and does not make its own baseline.
2. **Phase A: audit in parallel, read only.** Run the triage search from step 1 of "Convert many tests" on each spec first. A spec where every test hits a backend-only gate (real login, SSO, MFA, git sync, a real external database, a backend Snowplow event) gets no agent. Give it one line in the report. For each other spec, start a read-only audit agent, up to 8 at a time. Each one returns:
   - a verdict for every `it()`
   - for each `convert` row, the Jest spec, test helper and server-mock files it will edit
   - every E2E test it will name as cover

   Do not convert in this phase.
3. **Settle the protected list.** Merge all named covers into `target/e2e-to-unit/covers.md`. If a spec's `convert` row is a cover for another spec's row, the row stays in Cypress. Drop it from the work list. A spec with no `convert` row is done and gets no branch.
4. **Plan the branches.** Each spec with work gets the branch `e2e-to-jest-<folder>-<spec name>` (without `.cy.spec.*`), for example `e2e-to-jest-admin-databases`. It starts from the same base commit as the others. Two specs that edit the same Jest spec, test helper or server-mock file must not run at the same time. Put the second one in a stack: its branch starts from the first one's branch, after the first is done. Say in its PR that it is stacked on the first.
5. **Phase B: convert in parallel.** Each spec gets its own worktree on its own branch. Up to 4 workers run at a time, and a stacked spec waits for the spec below it. Each worker follows "Convert one test" for the rows of its spec only, with the audit from phase A. It does not audit again. It uses the shared type-check baseline. It does not touch any other Cypress spec. It does not commit.
6. **Check and commit each branch.** In each worktree, run the touched Jest specs as whole files, and check that each named cover test exists (search for its title). Then commit the spec's changes on its branch, if the user asked for commits. Otherwise give the commands. One branch holds one spec's changes only.
7. **Finish.** Report a table with one row for each spec: branch, tests moved, commit, and why the other tests stay. For each branch, write the PR title to `pr-<branch>.title` (in the form `test: rework <spec name> e2e spec to jest`, where the spec name has no `.cy.spec.*`, for example `test: rework databases e2e spec to jest`) and the PR body to `pr-<branch>.md` in the scratchpad, in the PR body format of "Judge Jest suitability", with permalinks at the branch's commit. Then write one script, `open-<folder>-prs.sh`, in the scratchpad. The script:
   - starts with `set -euo pipefail`, so it stops at the first error
   - for each branch, runs `git push -u origin <branch>`, then `gh pr create --head <branch> --base <base> --title "$(cat <title file>)" --body-file <body file>`
   - opens each stacked PR after the PR below it, with that branch as `--base`, and first gets that PR's number with `gh pr view <base branch> --json number --jq .number`, then writes the number into a copy of the stacked PR's body ("This PR is stacked on #<number>")
   - prints `done` at the end

   Check the script with `bash -n`. Do not run it. Give the user the command that runs it, with the absolute path. Say that the edited Cypress specs did not run, and list them for CI.

## Run a Cypress spec

- Use the `e2e-test` skill. If the spec calls `H.activateToken`, run it with `MB_EDITION=ee`. This skill's instruction counts as the user's request for an enterprise run. Check the tokens first, as `e2e-test` says.
- `bun test-cypress` reuses a backend that already runs on the Cypress port (`lsof -ti:4000`). If one runs, it must run from this checkout (`lsof -a -p <pid> -d cwd`). For a spec that calls `H.activateToken`, it must also have been started with `MB_EDITION=ee`. If not, or if you are not sure, do not use that backend. Treat the run as not possible (see below). Do not kill a backend that you did not start.
- If a kept or reduced Cypress test fails, fix only its setup, inside the spec file, then run the spec again. A setup fix may add or restore actions and intercepts. It never removes a check. Do not change a shared helper in `e2e/support` for this. The row is done only when the kept test passes. Never delete or weaken an assertion of a `keep E2E` claim or of a kept seam. If it still fails and you cannot fix it, undo that row's Cypress edits and mark the row `skipped` with the reason.
- If the failing test is one that no row changed, first copy the edited spec with `cp <spec> target/e2e-to-unit/<spec name>-edited`, and save each row's edited block next to its original as `row-<k>-cypress-edited.txt`. Then run the test alone (`GREP=<test title>`) with every row's Cypress edits to that spec undone. To put edits back, restore them from these saved files with the Edit tool. If it also fails then, record it as failing before your change, do not edit it, put the edits back, and do not skip any row. If it passes then, a row's edit broke it: put the edits back one row at a time to find that row, undo that row's Cypress edits, and mark it `skipped` with the reason. Among tests that no row changed, only a failure that a row caused can make a row `skipped`.
- If a required run cannot happen (no enterprise tokens, a backend from another checkout, no frontend build in `resources/frontend_client/app/dist` and no dev server on port 8080, or Docker not running; check these before the run), do the same: undo that row's Cypress edits, mark the row `skipped: Cypress run not possible (<reason>)`, and continue with the other checks. Never leave a reduced or trimmed Cypress test that did not run.

## Work in a new worktree

- Name the branch `e2e-to-jest-` plus the folder and the spec name, joined with `-`. For example, `e2e/test/scenarios/admin/databases.cy.spec.js` gets `e2e-to-jest-admin-databases`. One branch holds one spec.
- A new worktree has no `node_modules` and no compiled ClojureScript. Link `node_modules` from the main checkout (`ln -s <main checkout>/node_modules node_modules`, which git ignores), and run `bun run build-pure:cljs` once before the first Jest run. You can run the build in the background during the audit. Do not run `build:cljs` or `bun install`, because they write into the linked `node_modules`.
- Run backend tests with `./bin/test-agent`.
- A parallel worker runs `bun run build-pure:cljs` before any type check, then saves its own type-check baseline after `git apply`. It runs the type check with its own build-info file: `./node_modules/typescript7/bin/tsc --noEmit --tsBuildInfoFile target/e2e-to-unit/tsbuildinfo`, because the linked `node_modules` holds the shared one.
- Cypress cannot run in a new worktree, because it has no frontend build. A batch worker marks the rows that need a Cypress run, and the orchestrator runs them from the main checkout after their patch is applied. Any other agent in a worktree does not touch the main checkout: it treats the run as not possible (see "Run a Cypress spec"), and puts the undone Cypress edit in the report for the user to try.
- If the skill folder is not committed, the worktree does not have it. Read the skill from the main checkout path. This read, the `node_modules` link, a worker's read and `git apply` of the orchestrator's patch file and its copy of the listed files from the main checkout, and the orchestrator's copy of a worker's files override the `development-workflow.md` rule against files outside the project folder.
- Some sandboxes refuse long shell commands, such as a heredoc that runs Python. Write the script to a file, then run the file.

## Shell notes

- Keep this skill's work files (saved originals, worker patches) in `target/e2e-to-unit/` of the checkout (create it with `mkdir -p target/e2e-to-unit`). Git ignores `target/`, and the folder is inside the project, as `typescript-write` requires. A worker gives the orchestrator the absolute path.

- Run each `git` command alone, without `>` redirection or `;` and `&&` chains, and copy its output into your notes. Some sandboxes refuse a git command in a longer line. The same applies to `sed` chains.
- Write file paths literally in every command, not only in oxfmt, oxlint, and Jest commands. Quote glob patterns, for example `--include='*.spec.*'`, because zsh expands them and fails with `no matches found`. zsh does not split `$FILES` into words, so `bunx oxfmt --write $FILES` fails with `Expected at least one target file`. Some sandboxes also refuse a shell array, a shell variable, `xargs`, and a `for` loop or script that runs `git`. Write one plain command per file, or write the script to a file and run the file.
- A mutant can make lint or the type check fail. That is acceptable, because you run only Jest on a mutant.

Worked examples, each with the Cypress test, the replacement, the mutants, and the confidence lost:

- [references/dashboard-example.md](references/dashboard-example.md): a thunk test that reads request bodies. It also lists counterexamples that stay in Cypress.
- [references/component-example.md](references/component-example.md): a component test of a pending state, with `defer()`.
- [references/split-example.md](references/split-example.md): a permission claim split into a backend test and a component test.

Read the example that matches your behavior owner before you write the test.
