Search engine comparison

Where Metabase's search engines return different cards for the same query, and what each needs typed to find what a user wants.
These are hand-picked examples to explain the engines' behavior, not a sample of production traffic. They compare which cards come back, not their order, so they say nothing about ranking.

    Query matching rules

    Searches Live entity columns Materialized appdb text Indexed appdb lexemes Document embeddings
    Multiple words Any query word can suffice. Every query word must match. Every processed term must match, unless using operators. Compares the query's overall meaning; individual words need not match.
    Partial words Any substring: rate matches Moderated. Any substring, including inside longer words. Prefix of the final eligible word only; no inner substring. No defined prefix or substring rule.
    Operators Implicit OR across words; or, -, and quotes are literal text. Implicit AND across words; or, -, and quotes are literal text. Conjunction, disjunction, negation, and phrase matching. Contextual interpretation; no guaranteed Boolean or phrase operations.
    Language No stopword removal or stemming. No stopword removal or stemming. Stopwords and stemming follow the site locale or search-language setting. Stopwords and stemming are model-dependent.

    Semantic search unions these vector hits with keyword hits, then ranks the combined results. For every scenario here, the keyword hits are the appdb/PostgreSQL hits. Below its results threshold (100 by default), which a small catalogue always is, it also appends appdb's results, as long as its own arms found something. The pages score semantic search twice: Semantic only is the vector arm alone, and Semantic with fallback is what it returns, modelling appdb as PostgreSQL.

    Weights by kind of goal

    The means are exploratory. The goals were picked to expose differences between the engines, so they reflect that mix, not production traffic. Each kind's goals are averaged first, so a weight says how much that kind matters, not how many examples it has.

    Explore cases

    Agreement describes how the engines' result sets relate, ignoring order; it says nothing about which is right. “All agree” means all five return the same cards; “Four agree” means one engine differs; “Three and two agree” means two groups; “Three agree” means a group of three and two outliers; “Two pairs agree” and “One pair agrees” count matching pairs; “All differ” means no two engines match.

    Conformance compares each engine with the intended results declared for the comparison: how many return exactly those results? Those engines are highlighted in the case detail. The intended results describe what the user most likely meant, so it is possible for no engine to achieve them. Sorting by conformance breaks ties by mean F1, which gives partial credit for near misses.
