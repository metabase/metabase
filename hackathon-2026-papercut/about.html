Papercuts

Coding agents keep tripping on the same small things in our repo: a misleading test helper, a mage task with a hidden step, a zsh quirk. Papercuts spots them in finished agent sessions, groups repeat sightings, and lets anyone send one to a headless Claude Code fixer that opens a draft PR.

Importing past sessions alone gave 137 papercuts from about 290 reports. The most common one, zsh quirks in the Bash tool, was hit 36 times.

How a sighting becomes a papercut

Deduplication and classification happen in six steps. Two use AI judgement: the drill-down agent in step 3 when a sighting arrives, and Jev in step 5, which checks again for duplicates the agent missed. Only people merge.

  1. rule

    Read only what's new

    The scanner remembers where it stopped in each session and which papercuts the session already reported, so a session is never counted twice.scan.clj · local scan state
  2. Jev

    Screen cheaply

    Jev answers a few yes/no questions about each stretch, such as "did a tool give misleading output?". It only picks which stretches deserve a closer look. It never decides what is a papercut.jev.clj
  3. claude / codexthe judgement

    Decide, classify, match

    An agent reads the flagged stretch and decides whether it holds a real papercut. It classifies each one (kind, owner, severity) and cites the transcript lines that prove it. It also sees the list of open papercuts. If one is the same trap, the new sighting joins it. Otherwise the agent starts a new one.drill.clj · structured JSON answer
  4. server

    Group and count

    Reports with the same fingerprint land on the same papercut. A report the server has already seen is ignored. The first category a report sends sticks, and later ones show as votes.server.py · ingest
  5. Jevsecond look

    Flag likely duplicates

    When a papercut's text changes, the server picks up to 12 others that share its path or wording. Jev judges each one: duplicate, related or unrelated. Verdicts it's at least 50% sure of appear on the papercut's page with that probability. Pairs a person has already decided are never judged again.dispatcher.py relate
  6. peopleJev

    Merge and judge readiness

    On a flagged pair, people choose Merge, Related or Not related. Before a merge, the page shows which papercut stays, how many reports move, and whether triage resets. A merge can't be undone yet. Every decision is recorded under the person's Google account. Optionally, the dispatcher marks a papercut ready when it has enough evidence and Jev thinks it's fixable repo code. Enough evidence means two reporters, three reports, an hour lost, or high severity.web view · dispatcher.py assess

Why two AI steps. The agent in step 3 matches a sighting against every open papercut's title, and it sometimes misses a reworded duplicate. Step 5 reads full descriptions of a shortlist and costs one Jev call per changed papercut, so it catches most of what step 3 misses. A person still makes every merge.

What a merge does

A merge keeps one papercut and folds the other into it, in one transaction. You choose which one stays; the page suggests the one with more reports.

  • Reports and fingerprints move to the papercut that stays. Later sightings with the old fingerprint land there too, so the duplicate can't come back on its own.
  • The old papercut redirects. Links to it, in the browser and the API, lead to the one that stays.
  • Triage carries over only when both agree. If the two papercuts had different statuses or categories, the one that stays goes back to open to be triaged again. If it had no category, it takes the other's.
  • A fix in progress moves with it. A dispatch running on the merged papercut now works on the one that stays. When both have a dispatch running, the merge is refused.
  • Related links move too. Where both papercuts had a view on the same third papercut, a person's decision beats an AI suggestion.
  • History records it on both papercuts, with who merged, when and why.
  • The archive importer merges as well. A mined writeup that lists merged_from routes those slugs to its papercut and merges any papercut they already created.
  • There's no undo yet. Reports don't remember which papercut they came from, so a merge can't be reversed. That's on the to-do list.

What leaves your laptop

  • Secrets are redacted before anything is sent: API keys, tokens, passwords, private keys and connection strings.
  • Redacted chunks of new transcript go to TypeSafe Jev for screening.
  • Only flagged chunks go to the claude or codex CLI. That agent gets no tools, and its own session isn't saved.
  • Sessions that did embargoed security work are skipped whole.
  • The server receives the agent's write-up, with the transcript's path and the numbers of the lines it cites. It never receives the transcript text.

Try it

Opt in to automatic scanning from the repository root. The hooks run in the background when a session ends.

./bin/mage papercuts-install-hooks
./bin/mage papercuts-install-hooks --uninstall

Then browse metaouch.dev with your metabase.com account. Sort by reports, open a papercut, and press Dispatch on one you'd like fixed.

Running it

Hosting
metaouch.dev behind nginx with Google sign-in. Agents on the tailnet call port 8765 directly.
Storage
One SQLite file in WAL mode; migrates itself on start
Local server
python3 server.py --reload, port 8765
Fix runs
Needs claude, gh and LINEAR_API_KEY. Logs go to runs/<id>/
